# Attack rounds

Read at the attack step. Paths: `$S` is `${CLAUDE_SKILL_DIR}/scripts`, `$R` the repository's absolute path, `$O` the run folder.


Try to break the app on purpose. Before the first round, regrade with `--status running --step "Attack round 1: trying to break permissions and data"`. **Model.** The attacker and the verifier run on the models the user chose for Inspect's agents. Run `node $S/settings.mjs models`. If it says `unset`, ask once, in plain words, and save the choice with `node $S/settings.mjs models --set <choice>`:
- **Recommended:** the strongest model for attacking and for checking what was found. Higher cost.
- **Budget:** a faster, cheaper model for both. Lowest cost; attacks may miss more.

Without a user, use the `default` it prints. Spawn the attacker with its `attacker` model, and the verifier with its `verifier` model.

Before the first round, run `node $S/attack.mjs entries --out $O`: it lists the app's server entry points (API routes, route handlers, server actions, loaders, form actions, router routes) from the code. Tell the user, in one line, how many ways into the server the app has (not "entry points"). What the attacks reached is counted against this list from the attack tests' code, not from the attacker's report; `attack.mjs list` shows it under `entries`, and the grade lists each one not reached.

Each round, spawn the `imagineer:attacker` agent with the Agent tool (model: the `attacker` above) and give it, in its prompt: the copy's path (from `$O/copy.json`), `$O` and `$S`, each written out in full (it can run nothing but `attack.mjs` and read nothing outside these), the round number, the attack IDs to use (`attacksPerRound` from `attack.mjs list`: four in a Standard run, six in a Thorough one, continuing from the last), what the app is for and its roles, the user's answers from the ledger, and the attacks already tried and the parts not yet attacked (`node $S/attack.mjs list --out $O`: `untested`, and `entries.notReached`, the entry points no attack test touched). Point the next round at what is still untested first, entry points that handle money, personal data or permissions before the rest. On a later run of the same repository, `entries` says which ways in changed since the last run that attacked, or were never reached: those first; in a Standard run, leave out the ones an earlier run attacked that have not changed.

**Spare the attacker the setup.** Give it, in its prompt, how to run one test here: `detect.json`'s `layout.testSetup` (the command with `{file}` for the test's path, an example test, the TypeScript loader when there is no runner, and any note). From round 2, also `workingSetup` from `attack.mjs list`: the command that ran an earlier attack, with that attack's test to start from. Finding this out again costs a round's turns.

After each round:

1. Run `node $S/attack.mjs list --out $O`. Have each attack that broke through checked by the `imagineer:verifier` agent (as in step 5 of the skill: one spawn for the round's breaks, each given as `attack:<id>` with its test's file), never by you or the attacker. A break it rules a false alarm is set aside as a wrong test. A confirmed break that tried what a question in the ledger already asks is the same finding, not a new one: link it, `node $S/attack.mjs link --out $O --id A4 --question Q3`, and ask nothing new about it; the grade then counts it with that answer (kept if the user's answer is what the app does, a gap if they want it fixed), and a round whose breaks were all asked before counts as finding nothing new. For each other one it confirms, add it as a check for the user (topic `permissions` or `data`): the attack's situation as the example, stopping before what happened ("Carol, an approver on team A, opens Dave's expense from team B and presses Approve"), outcomes such as "The app refuses" and "The expense is approved", and `today` the one the attack showed. The user decides; Inspect does not fix it.
   Attacks it lists under `notRun` did not run (a test was skipped, most often for want of a database). They are not held: the grade lists them as not attacked yet, and so does your report, with the reason.
2. **Ask the questions this round raised now**, before the next round, as [questions.md](questions.md#asking) describes: the user is most likely there between rounds, and their answers aim the next one. A break left unasked waits for the next run, and the grade cannot count it as the user's decision until then.
3. Regrade with `--status running --step "Attack round <next>: trying to break permissions and data"` before the next round, or `--step "Cleaning up"` when the rounds are over.
4. **Stop** when 2 rounds in a row find nothing new, after the run size's rounds (two in a Standard run, four in a Thorough one), or when the user says so. In a Thorough run, ask before each round after the second. When `attack.mjs list` says `canStillFinish: false`, the rounds left cannot bring two clean rounds in a row: say so plainly when you ask ("Another round can't finish Inspect this run: rounds 1 to 3 each found something. Stop here, fix what was found, and run Inspect again?"), with stopping first.

Without a user, run two rounds, list what broke through, and stop.
